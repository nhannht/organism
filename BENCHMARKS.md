# Benchmarks

organism against orgize (Rust), go-org (Go), uniorg (JavaScript), and org-element itself
(Emacs, the reference), on identical bytes, two axes published together: how fast each parser
builds its tree, and whether that tree is right. Every number is reproducible from a clean
clone; the raw receipts are dated files under `bench/results/`.

The one-sentence result: **organism is the fastest full-fidelity org parser** - the only
parser measured here, other than org-element itself, that reproduces org-element's tree node
for node, and it is 9 times faster than org-element at the real-corpus median. Two parsers
post higher raw throughput: orgize by an order of magnitude, go-org by about 1.3x at the
median - and both fail roughly half the conformance suite, passing 67 and 59 of 121. The
nearest-accuracy competitor, uniorg at 81 of 121, is 13 times slower than organism at the
median. The field reduces to a two-point frontier: organism if the tree has to be right,
orgize if it only has to be fast; every other parser measured here is beaten on both axes by
one of those two.

"Full fidelity" is not a slogan, it is the strict row of the accuracy table below: the tree is
structurally identical to `org-element-parse-buffer`'s own answer - every node type, every
field, every blank-line count - on all three corpora, including the entire test corpus of one
of the competitors.

## Accuracy: every parser against org-element's own answers

Graded 2026-08-08 by `bench/accuracy/grade.py` on three corpora: the 121 hand-written
conformance cases, the 28 vendored real-world files, and the 1,505-case generated differential
sweep. The reference answer for every case is org-element's own tree (Emacs 30.2 / org
9.7.11). `strict` = tree identical; `structure` additionally admits trees that match after
stripping blank-line bookkeeping (`postBlank`/`preBlank`).

| parser | conformance (121) | real files (28) | sweep (1,505) |
|---|---|---|---|
| **organism** | **121** strict | **28** strict | **1,505** strict |
| org-element (control) | 121 strict, live run | by construction | by construction |
| uniorg-parse 3.2.2 | 81 strict / 81 structure | 13 / 17 | 693 / 698 |
| orgize 0.9.0 | 67 / 68 | 2 / 3 | 402 / 404 |
| go-org v1.7.0 | 59 / 59 | 1 / 1 | 479 / 479 |

No parser crashed on any input; every failure is a wrong tree or a declared AST capability
gap. The full verdict taxonomy (`cannot-represent` vs `wrong-tree`), the per-case TSVs with
the first divergence pinned, and the per-parser breakdown live in
`bench/results/accuracy-2026-08-08/`.

Three things keep this table honest, because the corpora live in this repository and organism
was developed against them while the competitors were not:

- **The answers are org-element's, not ours.** Every expected tree is generated by
  `harness/oracle-dump.el` running real Emacs. organism's row is graded through the same
  external pipeline as every competitor (its CLI JSON output, diffed by the same script), not
  through its own test suite. The org-element control row is re-run LIVE at grading time and
  doubles as the fixture drift check.
- **Each competitor got a real adapter, under written fairness rules.** A thin adapter per
  competitor re-encodes ITS emitted AST into the schema shape - never re-parsing the source,
  never guessing missing fields - and failures on information the competitor's AST cannot even
  carry are classified `cannot-represent`, separately from parse bugs. The rules, the
  per-adapter judgment calls, and the hand-audit of every conformance `wrong-tree` verdict are
  in `bench/accuracy/README.md`.
- **One corpus is a competitor's own.** `real/go-org-testdata/` is go-org's entire test
  corpus, vendored unmodified. organism parses all 15 files oracle-perfect; go-org's own
  strict score on the full real-file corpus is 1 of 28, because its renderer-oriented AST
  stores no blank-line information and only one timestamp form.

Reproduce:

```bash
swift build -c release --package-path bench
(cd bench/competitors/orgize && cargo build --release --bin orgize-adapter)
(cd bench/competitors/go-org && go build -o go-org-adapter.bin ./adapter)
python3 bench/accuracy/grade.py --out bench/results/accuracy-YYYY-MM-DD
```

## Speed: parse throughput on identical bytes

Measured 2026-08-09 by `bench/run-all.sh` under the protocol in `bench/README.md`: parse
only (file read and decoded before the timed loop), each parser building its own NATIVE tree
(no adapter code in any timed loop), self-timed with the language's monotonic clock (process
startup and JIT warmup never enter a number), warmup then median over a 1-second budget per
file, single-threaded. Raw TSV: `bench/results/2026-08-09-all.tsv`.

Throughput in MiB/s, higher is better. The seven synthetic files are ~1 MiB each, generated
deterministically by `orgbench gen`, each stressing one region of the grammar; the two fetched
files are org-mode's own manual and compact guide, the largest well-known real org documents.

| file | organism | orgize | go-org | uniorg | org-element |
|---|---|---|---|---|---|
| syn-prose.org | 24.30 | 220.37 | 59.43 | 1.59 | 3.03 |
| syn-emphasis.org | 27.58 | 84.66 | 47.50 | 0.04 | 0.76 |
| syn-lists.org | 22.20 | 198.02 | 17.51 | 0.21 | 1.21 |
| syn-tables.org | 31.19 | 75.89 | 31.81 | 0.24 | 1.45 |
| syn-links.org | 25.31 | 440.04 | 106.43 | 1.39 | 6.19 |
| syn-outline.org | 23.17 | 223.82 | 33.34 | 3.64 | 2.54 |
| syn-radio.org | 10.26 | 463.89 | 111.66 | 0.10 | 7.82 |
| org-manual.org | 16.73 | 199.94 | 22.21 | 1.64 | 2.67 |
| org-guide.org | 21.12 | 267.56 | 25.30 | 1.63 | 2.64 |

Two rows deserve their own sentence. syn-radio is the one profile where organism deliberately
parses TWICE (radio targets force a second pass; a document defining none skips it), so its
number is the honest price of that design. And syn-emphasis is where uniorg and org-element
collapse - 23 seconds and 1.3 seconds per MiB respectively on emphasis-dense text - which is a
result about them, not an artifact: the rows were re-measured in isolation and reproduced.

Across the 28 vendored real-world files (small files, so per-parse overhead matters more than
streaming throughput), median MiB/s per parser: organism 16.2 (per-file range 5.8 to 33.6),
orgize 249, go-org 21.8, uniorg 1.2, org-element 1.8. Per-file rows are in the TSV.

Reproduce:

```bash
(cd bench && swift build -c release && ./.build/release/orgbench gen corpus/synthetic)
bash bench/fetch-bench-corpus.sh
bash bench/run-all.sh
```

## The two axes together

```
  conformance, strict (of 121); x = median MiB/s across the 28 real files, log scale
      |
  121 |                  * org-element (1.8)
  121 |                               * organism (16.2)
      |
   81 |               * uniorg (1.2)
      |
   67 |                                                * orgize (249)
   59 |                                 * go-org (21.8)
      |
      +--------------+-------------+-------------+------->
                     1            10            100    MiB/s
```

Read it either way. Fix correctness at 121 of 121 and organism is the only parser in that
column besides the reference itself, at 9 times the reference's speed - 4 to 36 times on
eight of the nine large files, 1.3 times on syn-radio, the profile built to force its
two-pass path. Fix speed and ask what the fastest tree is worth: orgize's throughput is real
and organism does not match it, but 54 of its 121 conformance trees are wrong or
unrepresentable, as are 73 percent of the sweep's. Nothing on the chart sits above and to the
right of organism: every parser is either slower, or wrong about the tree, and the two that
are faster are wrong about roughly half of it. orgize itself makes the same trade from the
other side - it beats go-org on both axes, so the five-parser field collapses to a two-point
frontier: organism and orgize, fidelity and throughput.

## Environment

One machine, one thread: Apple M5 (10 cores), 24 GB, macOS 26.6. Emacs 30.2 / org-mode
9.7.11; toolchain versions are recorded in the header of each results TSV. The sweep ran at a
load average of roughly 4 with desktop apps live - not a lab machine - which is why the
protocol reports medians with the per-row minimum as the noise floor, and why one file's rows
were re-measured in isolation when a background render polluted their window (the note in the
TSV header, the full three-measurement record in `bench/results/deltas.md`).

Competitor versions are pinned by lockfile (`Cargo.lock`, `go.sum`, `pnpm-lock.yaml`), and
each accuracy adapter lives beside its speed runner sharing that same lockfile - the accuracy
table grades exactly the builds the speed table times.

## Honest limits

- **Cross-machine absolute MiB/s is meaningless.** The ratios are the result. Run
  `bench/run-all.sh` on your own machine for your own absolutes.
- **Speed says nothing about correctness, which is why both tables are published together.**
  A fast parser that builds a wrong tree is fast at something else.
- **The competitors did not sign up for this fidelity bar.** go-org feeds an HTML renderer and
  its AST deliberately stores less than org-element does; orgize optimizes for speed and its
  0.9 AST drops affiliated keywords and link types by design. The `cannot-represent` column
  exists so those design choices are not misread as parse bugs. What the strict column says is
  narrower and true: if you need org-element's tree, these parsers cannot give it to you.
- **The corpora are this repository's.** Mitigations above (org-element authored every
  answer, the sweep is generated, a competitor's own corpus is included, the control row runs
  live), but an independent replication on a corpus this project has never seen would be
  stronger evidence, and the suite is published precisely so someone else can run it.
- **org-element's speed row is org running batch inside Emacs** (`org-element-parse-buffer`
  timed in-process, buffer pre-loaded). It is the reference for trees, not a speed contender,
  and its numbers are shown for scale.
- **uniorg's numbers are Node.js numbers.** V8 warmup is excluded by the protocol (unmeasured
  warmup, in-process timing), but a JIT runtime on a 1-second budget still has more variance
  than the compiled runners; treat small deltas on its rows as noise.
