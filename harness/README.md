# harness/

This directory holds every script that talks to real Emacs, plus the one script that runs the
full Layer 1 check-loop end to end without needing a working Swift parser. Nothing here is
Swift. A parser author in any language can call these same scripts directly.

Requires Emacs 27 or later, for native `json-serialize`/`json-parse-string` support. This
project develops and tests against Emacs 30.2 with org-mode 9.7.11. Run `emacs --version` and
`emacs --batch --eval '(princ (org-version))'` to check what you have. All commands below assume
you are in the repo root.

## oracle-dump.el

The core oracle. Parses one `.org` file with Emacs's own `org-element-parse-buffer`, then walks
that tree and re-emits it as the exact JSON shape `SCHEMA.md` defines - the same shape
`parseOrg` must produce.

```bash
emacs --batch -Q -l harness/oracle-dump.el --eval '(org-swift-dump "conformance/easy-heading-levels/input.org")'
```

Prints one JSON document to stdout. Warnings (an org-element node type this script does not yet
map) go to stderr via `message`, never to stdout, so stdout always stays parseable JSON even when
something is off.

Every `conformance/*/expected.json` file in this repo was generated by running this exact
command against that case's `input.org`. This matters for reading test results correctly: a
green run of `Tests/OrgSwiftTests/OracleConformanceCrossCheckTests.swift`, or of
`verify-corpus.sh` below, proves `oracle-dump.el`'s output has not drifted from the answer key it
originally produced. It does NOT independently prove the answer key is correct org-mode
behavior, because the answer key came from the same oracle it is compared against. See
`SCHEMA.md` section 9 ("RESOLVED: reference-faithful normalization") and that Swift suite's own
docstring for the full reasoning.

## interpret-data-check.el

The actual independent correctness check, and a different question from `oracle-dump.el`
entirely. It never touches `OrgJSON` or any of this project's own JSON shape. It asks only:

```
org-element-interpret-data(org-element-parse-buffer(file)) == file's own bytes?
```

```bash
emacs --batch -Q -l harness/interpret-data-check.el --eval '(org-swift-check-roundtrip "real/org-mode-samples/blocks.org")'
```

Prints one JSON object: `{"match": true}` or `{"match": false, "originalLength": N,
"interpretedLength": M, "firstDiffOffset": K, "originalContext": "...", "interpretedContext":
"..."}`. A match proves `org-element`'s own parse tree - not this project's JSON projection of
it, `org-element`'s own tree - carries enough information to reconstruct the source exactly,
using only `org-element`'s own parse and unparse functions. That was the empirical basis for
going reference-faithful in the first place (`SCHEMA.md` section 1): if buffer positions really
are redundant here, a schema that keeps everything else BUT positions can, in principle,
round-trip too.

Run across all 52 conformance inputs plus the 13 vendored real-world files (65 total), 41/65
matched byte-for-byte on a live Emacs 30.2 run. The 24 that did not are documented and classified
in `Tests/OrgSwiftTests/InterpretDataRoundTripTests.swift` (`knownReformattingDivergences`) and
in `SCHEMA.md` section 10 - each traces to a known `org-element-interpret-data` re-emit
convention (keyword-name case-folding, block/property-drawer reindentation, and so on), not to a
byte silently lost from the parse tree, except for the small, named set of genuine losses section
10 calls "Reason A" and "Reason B".

## verify-corpus.sh

The runnable reference adapter for Layer 1. `parseOrg` does not exist yet (see the repo root
`SCHEMA.md` section 8), so it cannot fill the "parse -> normalize -> diff against expected.json"
loop. `oracle-dump.el` already does exactly that loop for Emacs itself, so this script runs it
over every conformance case and reports a real pass/fail count - Emacs stands in for "your
parser" here, so a reader can see the whole check working before a single line of this project's
own parser exists.

```bash
bash harness/verify-corpus.sh
```

For each of the 52 `conformance/<case>/{input.org,expected.json}` pairs: runs `oracle-dump.el` on
`input.org`, canonicalizes both that output and `expected.json` with `jq -S` (recursively sorted
object keys, so key order never causes a false mismatch), and diffs the two. Prints one
`PASS`/`FAIL` line per case plus a final summary line, and exits non-zero if any case failed.
Requires `emacs` and `jq` on `PATH`; degrades to a clear `SKIP:` message and exit 0 if either is
missing, never a silent pass. Read-only: it only reads `conformance/` and writes to its own
self-cleaning temp directory, never into `conformance/` or `real/`.

Same caveat as `oracle-dump.el` above applies here too, since this script calls it directly: a
green run confirms `oracle-dump.el` still agrees with the answer key it generated, which is a
real and useful regression signal (an Emacs/org-mode version bump, or an edit to `oracle-dump.el`
itself, would show up here as new `FAIL` lines), but it is not a from-scratch proof that
`expected.json` is correct org-mode behavior. That from-scratch check is
`interpret-data-check.el` above.

If this script reports a `FAIL` for a case, before assuming the fixture is wrong: re-read that
case's `input.org` by hand against `SCHEMA.md`'s relevant section, then check
`Tests/OrgSwiftTests/InterpretDataRoundTripTests.swift`'s `knownReformattingDivergences` set for
whether the same file already shows a known, benign `org-element-interpret-data` re-emit quirk -
a different check, but a useful cross-reference for "is this Emacs being weird, or is the fixture
actually wrong." A genuine disagreement between `oracle-dump.el` and `expected.json` that is not
explained by a known reformatting convention is a real bug: either a recent edit to
`oracle-dump.el` regressed a mapping, or an Emacs/org-mode upgrade changed real parsing behavior.
Fix the elisp (or, if `expected.json` and the schema are the ones that need to change, edit the
fixture and note why in a commit message), then re-run this script and `swift test` before
trusting the corpus again.

## fetch-corpus.sh

Unrelated to the oracle. Downloads the copyleft (GPL/GFDL) real-world `.org` corpus - Worg and
org-mode's own official test files - into `real-fetched/`, which is gitignored and never
committed. See that script's own header comment and `NOTICE.md` for exactly what it fetches and
why those files cannot be vendored the way `real/` is.

```bash
bash harness/fetch-corpus.sh
```

Safe to run more than once; each run wipes and re-clones its own working directory.
